# Registro de riscos técnicos e ações propostas

Este é um diagnóstico estático do repositório público. Não comprova vulnerabilidade explorável em produção: o resultado final depende de grants, políticas RLS, configurações do Supabase e eventuais migrações executadas fora do repositório. Nenhuma operação foi executada contra o banco de produção.

| ID | Severidade inicial | Evidência no repositório | Risco/impacto | Ação proposta |

| SEC-01 | P0 a confirmar | migrations/016_security_rpcs.sql: viajar_mapa, aprender_jutsu, aprender_jutsus_massa, vip_reset_talento e vip_reset_personagem usam comparação v_user_id != auth.uid() em funções SECURITY DEFINER. | Se auth.uid() for NULL, a expressão != pode resultar em NULL e o IF não rejeita a chamada. A exposição depende dos grants de execução. | Usar auth.uid() IS NULL OR v_user_id IS DISTINCT FROM auth.uid(); validar registro existente; adicionar SET search_path seguro e qualificar objetos; restringir EXECUTE a roles necessárias. |

Não confirma objetivo/pré-requisito concluído. | Se a função puder ser chamada pelo jogador autenticado, pode haver conclusão/recompensa para personagem alheio ou progresso indevido. | Validar proprietário, objetivo e pré-requisitos no banco; lock transacional; limitar grants; garantir recompensa idempotente. |

## Ordem sugerida de correção

1. Inventariar RLS/policies e privilégios EXECUTE no ambiente Supabase.
2. Corrigir autorização e contratos de funções sem mudar fórmulas do jogo.
3. Tornar missões, comércio e recompensas transacionais/idempotentes.
4. Centralizar a resolução do combate e validar entradas.
5. Adicionar testes de regressão e só então alinhar fórmulas.

## Limitação operacional
Não há conexão de execução SQL do Supabase disponível nesta tarefa. Portanto, o banco de produção não foi alterado nem inspecionado diretamente. Qualquer migration futura precisa de revisão de compatibilidade, backup e execução deliberada pelo canal de deploy aprovado.
